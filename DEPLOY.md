# Установка rust-file-manager на VPS

Начните с [простого алгоритма](DEPLOY_ALGORITHM.md). Этот файл — справочник
установки: команда `deploy` для пустого VPS, HTTPS и ручная установка.
Обновление, повторная установка, откат и перенос на другой сервер —
[POST_DEPLOY.md](POST_DEPLOY.md).

| Команда | Назначение |
|---|---|
| `deploy` | установить файловый менеджер, nginx и HTTPS, если их нет |
| `post_deploy` | обновить установленный файловый менеджер; параметры в POST_DEPLOY.md |
| `rfm-vps status` | показать текущую установку |

Команды рассчитаны на Debian/Ubuntu с systemd и запускаются под root.
Все домены и адреса ниже — примеры. Пароли и ключи вводятся или создаются на
сервере, хранятся в закрытых настройках и не добавляются в Git. Эти команды
ставят только файловый менеджер; Telegram-бот и мини-приложение по желанию
подключаются отдельно ([раздел ниже](#telegram-бот-и-мини-приложение)).

На минимальном сервере сначала нужен только curl (git, nginx, certbot и
средства сборки `deploy` поставит сам):

```bash
apt-get update && apt-get install -y curl ca-certificates
```

Интерактивные команды вводите по одной: следующая строка не должна стать
ответом на вопрос установщика. Подготовьте A-запись своего домена; AAAA
должна соответствовать настроенному IPv6. Перед новым ufw согласуйте порты
уже работающих на сервере приложений.

## Установить команды на сервер

Один раз на каждом сервере, под root:

```bash
curl -fsSL https://raw.githubusercontent.com/kureinmaxim/rust-file-manager/main/deploy/rfm-vps.sh | bash -s -- setup
```

`setup` ставит в `/usr/local/sbin`:

- `rfm-vps` — сам скрипт;
- `deploy`, `post_deploy`, запасное имя `post-deploy` и `delete` — ссылки на
  него (`delete` — удаление, см. [ниже](#удалить-файловый-менеджер--delete)).

Ожидается сообщение `команды установлены` и короткая подсказка.

**Если хотите сначала прочитать скрипт.** Однострочник выполняет скрипт из
публичного репозитория от root, так же как установщик Docker. Можно сделать
это в три шага:

```bash
curl -fsSLO https://raw.githubusercontent.com/kureinmaxim/rust-file-manager/main/deploy/rfm-vps.sh
less rfm-vps.sh
bash rfm-vps.sh setup
```

**Обновлять команды вручную не нужно.** Перед обычным запуском `deploy` и
`post_deploy` сверяются с репозиторием и при отличии обновляются сами,
сохранив прежний скрипт в `/usr/local/sbin/rfm-vps.backup.*`.
`post_deploy --check` сам скрипт не заменяет. `setup` не перезаписывает
чужую команду с именем `deploy`, `post_deploy`, `post-deploy` или `delete`, в том числе
полную версию этих команд (`tgo-vps`), которая ставит файловый менеджер вместе
с ботом автора.

## Установить файловый менеджер

```bash
deploy
```

### Порядок работы

1. **Показывает, что стоит на сервере.** Если файловый менеджер уже
   установлен, только доделывает отложенное (см. ниже).
2. **Сразу задаёт все вопросы.** После ответов работает без вас.
3. **Проверяет порты и место на диске** до установки пакетов и сборки.
   Программе нужен порт на localhost: обычно 8080, а если его держит другая
   служба (например, координатор Headscale или XHTTP), команда берёт первый
   свободный из 8081–8099 и показывает его в плане. Порты HTTPS — 80 и 443 для
   certbot или 2083 для Cloudflare: если их держит не nginx, установка
   останавливается с именем процесса. Первой сборке нужно 2 ГБ свободного места.
4. **Ставит пакеты:** git, curl, openssl, build-essential, pkg-config; nginx —
   если HTTPS через него (`certbot` или `cloudflare`), certbot — при certbot,
   ufw — только если его включаете.
5. **Готовит сервер:**
   - создаёт swap 2 ГБ, если его нет, памяти меньше 3,5 ГБ, а на диске
     после этого останется место для сборки (свободно от 4 ГБ). Уже
     включённый swap команда не трогает, даже маленький: если памяти вместе
     со swap меньше 3 ГБ (например, 1 ГБ и swap 1 ГБ), добавьте swap до
     `deploy` — последний шаг сборки (LTO) требует много памяти:
     ```bash
     [ ! -e /swapfile2 ] && fallocate -l 2G /swapfile2 && chmod 600 /swapfile2 &&
       mkswap -q /swapfile2 && swapon /swapfile2 && echo '/swapfile2 none swap sw 0 0' >> /etc/fstab
     ```
   - включает ufw, если вы согласились.
6. **Ставит файловый менеджер:**
   - ставит Rust;
   - скачивает код в `/root/rfm-build` и собирает в фоне. Ход сборки виден на
     экране раз в 15 секунд, журнал — `/root/rfm-build.log`;
   - создаёт пользователя `filemgr` и каталоги, ставит программу;
   - пишет настройки `/etc/rust-file-manager/env` с паролем и ключами;
   - ставит службу systemd, запускает её и проверяет.
7. **Настраивает nginx и HTTPS** выбранным способом.
8. **Проверяет всё** и пишет итог и что осталось сделать вручную. Среди
   проверок — что другие службы сервера на месте: порты, которые слушали до
   начала команды (VPN, tailscaled, DERP, Headscale и др.), слушают и после.

### Вопросы

| Вопрос | Варианты | По умолчанию | Когда спрашивается |
|---|---|---|---|
| Домен файлового менеджера | например `files.example.com`; A-запись должна указывать на сервер | — | всегда при установке |
| Способ HTTPS | `certbot` — порт 443 свободен; `cloudflare` — через Cloudflare на 2083; `none` — свой прокси | `certbot`, а если 443 занят — `cloudflare` | всегда при установке |
| Почта для Let's Encrypt | адрес или Enter | без почты | при `certbot` |
| Логин администратора сайта | любой | `admin` | всегда при установке |
| Пароль администратора | от 8 символов, дважды, ввод не виден | — | если ещё нет настроек |
| Включить ufw | да или нет | да; **нет**, если на сервере уже слушают другие службы | если ufw выключен |
| Начинаем? | да или нет | да | всегда, после показа плана |

Неверный домен, короткий или несовпавший пароль переспрашиваются.

**Порт SSH для ufw** берётся из текущего подключения. Если его не видно,
например в консоли провайдера, а не по SSH, ufw не включается, чтобы не
потерять доступ.

**Сервер с другими службами.** Если ufw выключен, а внешние порты уже слушают
другие программы (VPN, панели и т. п.), команда показывает их список и по
умолчанию ufw не включает; `--yes` его тоже не включает. При явном согласии
или `ENABLE_UFW=yes` перед включением разрешаются все порты, которые сейчас
слушают службы (TCP и UDP, кроме loopback). Остановленная в этот момент служба
окажется закрыта — включайте ufw, когда все нужные программы запущены.

Для HTTPS через Cloudflare нужен ещё **Origin-сертификат**: `cert.pem` и
`key.pem` в `/etc/nginx/ssl/files.example.com/`. Лучше положить их до
`deploy`: тогда nginx на 2083 настроится в том же запуске. Положили после —
запустите `deploy` ещё раз (подробно — [HTTPS через Cloudflare](#б-https-через-cloudflare)).
В Cloudflare:

- у записи домена **Proxied** (оранжевое облако): с DNS only браузер придёт
  на 443 сервера;
- режим SSL/TLS **Full (strict)**; если в зоне есть другие Proxied записи —
  Configuration Rule только для этого домена;
- Origin Rule на порт 2083;
- Bypass cache для `/api/*` и `/d/*`.

Если у провайдера есть свой файрвол, откройте в нём TCP 2083.

### Повторный запуск

**Повторный `deploy` безопасен.** Он ничего не переустанавливает и не меняет
существующие настройки, а только доделывает отложенное:
- nginx на 2083 после того, как положили сертификат Cloudflare;
- сертификат Let's Encrypt, если DNS в прошлый раз ещё не обновился.

**Если оборвался SSH**, запустите `deploy` снова: сборка продолжается в
фоне, и команда её дождётся.

### Без вопросов

Ответы можно задать переменными окружения и добавить `--yes`. Пароль
спрашивается всё равно:

```bash
RFM_DOMAIN=files.example.com HTTPS_MODE=certbot LE_EMAIL=admin@example.com \
ENABLE_UFW=yes deploy --yes
```

| Переменная | Значения |
|---|---|
| `RFM_DOMAIN` | домен файлового менеджера |
| `HTTPS_MODE` | `certbot`, `cloudflare`, `none` |
| `LE_EMAIL` | почта для Let's Encrypt |
| `RFM_ADMIN_LOGIN` | логин администратора, по умолчанию `admin` |
| `ENABLE_UFW` | `yes`, `no` |

Файловый менеджер умеет открываться как мини-приложение Telegram и принимать

## Ручная установка

Этот способ нужен для собственной раскладки. Для стандартного VPS используйте
`deploy`: он выполняет те же шаги.

### 0. Проверить сервер и выбрать схему HTTPS

```bash
uname -sm
free -h
df -h / /var/tmp /usr/local/bin
sudo ss -tlnp
```

Приложение слушает `127.0.0.1:8080`, наружу его отдаёт существующий reverse
proxy. Проверьте, свободен ли 8080 и кто уже занимает 80/443. Если там
работают Caddy, VPN или другие сайты, используйте их действующую схему либо
добавьте отдельный nginx-блок, не заменяя общую конфигурацию.

| Ситуация | Способ HTTPS |
|---|---|
| nginx может обслуживать 80 и 443 для домена | Let's Encrypt / Certbot, шаг 4А |
| 443 занят другим сервисом, домен через Cloudflare | Origin CA + nginx на 2083 + Origin Rule, шаг 4Б |
| Доступ через Tailscale/Headscale | [TAILSCALE.md](TAILSCALE.md); сертификат и cookie зависят от HTTP/HTTPS |

A-запись должна указывать на ваш VPS. При включённом Cloudflare-прокси
запрос идёт через Cloudflare; меняйте DNS только при изменении сервера.

### 1. Собрать и установить выбранный выпуск

Нужен **Rust 1.88 или новее**. Это максимальное заявленное требование
закреплённых зависимостей, включая Actix Web и time. На машине сборки:

```bash
sudo apt update
sudo apt install -y build-essential pkg-config git curl ca-certificates
```

Если Rust ещё не установлен, установите его для пользователя, который
собирает приложение, по [инструкции rustup](https://rust-lang.github.io/rustup/installation/index.html):

```bash
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
. "$HOME/.cargo/env"
rustc --version
cargo --version
```

Если установленный Rust ниже требуемой версии, обновите выбранный toolchain
через `rustup update stable`. Если действует override на старую версию,
выберите `rustup override set stable` в новом сборочном каталоге. Рабочий
бинарник от этого не меняется.

Соберите выбранную ветку или тег в отдельном каталоге, сохраняя существующие клоны.
Вместо `EXPECTED_FULL_COMMIT_SHA` укажите полный коммит выбранного выпуска
из доверенного репозитория перед выполнением блока:

```bash
RFM_RELEASE=main
RFM_COMMIT=EXPECTED_FULL_COMMIT_SHA
RFM_BUILD_DIR=$(mktemp -d "$HOME/rfm-build.XXXXXX")
git clone --depth 1 --branch "$RFM_RELEASE" \
  https://github.com/kureinmaxim/rust-file-manager.git "$RFM_BUILD_DIR" &&
cd "$RFM_BUILD_DIR" &&
test "$(git rev-parse HEAD)" = "$RFM_COMMIT" &&
CARGO_BUILD_JOBS=1 cargo build --release --locked --bin rust-file-manager
```

`--locked` сохраняет версии из `Cargo.lock`; не выполняйте `cargo update`
при обычном развёртывании. При переходе на другой выпуск замените ветку/тег и
ожидаемый коммит. Продолжайте установку только после успешной сборки.

Шаблоны, CSS и JavaScript встроены в бинарник: отдельные файлы фронтенда на
VPS копировать не нужно. Бинарник macOS на Linux не работает; при сборке на
другой машине должны совпадать Linux-архитектура и совместимость системных
библиотек. Самый простой вариант — сборка на целевом VPS.

На VPS с малой памятью повторите сборку с `CARGO_BUILD_JOBS=1`. Если памяти
всё ещё недостаточно, используйте другую Linux-машину или отдельно
подготовьте swap с учётом файловой системы и места на диске.

Только для новой установки, где бинарника ещё нет:

```bash
sudo test ! -e /usr/local/bin/rust-file-manager &&
sudo install -o root -g root -m 0755 \
  "$RFM_BUILD_DIR/target/release/rust-file-manager" \
  /usr/local/bin/rust-file-manager
```

Для замены существующего бинарника используйте [POST_DEPLOY.md](POST_DEPLOY.md).

### 2. Создать пользователя, каталоги и настройки новой установки

Служба работает от отдельного пользователя `filemgr`:

```bash
id filemgr >/dev/null 2>&1 ||
  sudo useradd --system --user-group --home-dir /var/lib/rust-file-manager \
    --shell /usr/sbin/nologin filemgr
sudo install -d -o filemgr -g filemgr -m 0750 \
  /var/lib/rust-file-manager /var/lib/rust-file-manager/uploads
sudo install -d -o root -g root -m 0755 /etc/rust-file-manager
```

Создайте секреты **только при первичной установке**. Для пароля используйте
скрытый ввод, чтобы сам пароль не попал в историю команд:

<!-- WARNING: вывод хеша пароля или SESSION_SECRET в терминал сохраняет их
в scrollback и журнале SSH-клиента. Генерируйте их в закрытые файлы. -->

```bash
umask 077
RFM_SECRET_DIR=$(mktemp -d "${TMPDIR:-/tmp}/rfm-secrets.XXXXXX")
IFS= read -r -s -p 'Пароль администратора: ' RFM_ADMIN_PASSWORD
printf '\n'
printf '%s' "$RFM_ADMIN_PASSWORD" | /usr/local/bin/rust-file-manager hash-password \
  > "$RFM_SECRET_DIR/password_hash"
unset RFM_ADMIN_PASSWORD
openssl rand -base64 64 | tr -d '\n' > "$RFM_SECRET_DIR/session_secret"
```

Через локальный редактор перенесите значения из `password_hash` и `session_secret`
в `/etc/rust-file-manager/env`, затем удалите временный каталог `RFM_SECRET_DIR`.
Не выводите эти файлы через `cat`, не присылайте их в чат и не добавляйте в Git.
Создание файла ниже
выполнится только при его отсутствии:

```bash
sudo test ! -e /etc/rust-file-manager/env &&
sudo install -o root -g root -m 0600 /dev/null /etc/rust-file-manager/env &&
sudoedit /etc/rust-file-manager/env
```

Содержимое с заменёнными значениями:

```ini
BIND_ADDR=127.0.0.1:8080
UPLOAD_DIR=/var/lib/rust-file-manager/uploads
USERS_FILE=/var/lib/rust-file-manager/users.json
ADMIN_USERNAME=admin
ADMIN_PASSWORD_HASH='$2b$12$...вставьте-полный-хеш...'
SESSION_SECRET=вставьте-base64-строку
MAX_FILE_SIZE_MB=200
COOKIE_SECURE=true
RUST_LOG=info
```

Не используйте `source` для этого файла: его читает `EnvironmentFile`
службы. Одинарные кавычки вокруг bcrypt-хеша подходят этому формату и
обязательны при переносе значения в `.env`, который читает dotenvy.
`SESSION_SECRET` должен декодироваться минимум в 64 байта: иначе приложение
создаёт случайный ключ и вход сбрасывается после рестарта.

При HTTPS используйте `COOKIE_SECURE=true`. Для отдельного доступа по HTTP
через tailnet такая cookie не отправляется; выбор схемы описан в
[TAILSCALE.md](TAILSCALE.md). При обновлении сохраните действующие секреты.

### 3. Установить systemd-службу

Стандартный юнит — [deploy/rust-file-manager.service](deploy/rust-file-manager.service):

```bash
sudo install -o root -g root -m 0644 deploy/rust-file-manager.service \
  /etc/systemd/system/rust-file-manager.service
sudo systemctl daemon-reload
sudo systemctl enable --now rust-file-manager.service
sudo systemctl is-active rust-file-manager.service
curl --fail --silent --show-error --max-time 10 \
  -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/login
```

Ожидаются `active` и `200`. При ошибке старта сначала прочитайте журнал
службы. Юнит разрешает запись в `/var/lib/rust-file-manager`; если данные
размещены иначе, согласуйте `WorkingDirectory`, `ReadWritePaths` и
права пользователя с фактическими путями. Не копируйте этот пример поверх
настроенной службы при обычном обновлении.

### 4. Reverse proxy и HTTPS

#### А. nginx обслуживает стандартные порты

Этот пример применим, если nginx может использовать 80/443. На сервере с
готовым proxy настройте отдельный виртуальный хост в его конфигурации.

```bash
sudo apt install -y nginx certbot python3-certbot-nginx
sudo cp deploy/nginx.example.conf /etc/nginx/sites-available/files.example.com
sudo sed -i \
  's/example\.com/files.example.com/g; s/client_max_body_size 200M;/client_max_body_size 201M;/' \
  /etc/nginx/sites-available/files.example.com
sudo ln -s /etc/nginx/sites-available/files.example.com \
  /etc/nginx/sites-enabled/files.example.com
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d files.example.com
sudo certbot renew --dry-run
```

Замените `files.example.com` в командах на свой домен. Не удаляйте
`sites-enabled/default` и другие сайты без проверки, для чего они нужны.
Перед Certbot сохраните nginx-конфигурацию; плагин меняет её для HTTPS.

<a id="https-через-cloudflare"></a>

#### Б. HTTPS через Cloudflare

Пошаговая схема — [GUIDE_cloudflare.md](GUIDE_cloudflare.md): Origin CA,
nginx на 2083, Origin Rule для нужного hostname, SSL/TLS **Full (strict)**.
Cloudflare поддерживает HTTPS на 2083. Настройте лимит nginx с запасом по
шагу 5. При обновлении приложения уже работающие сертификаты и правила
Cloudflare заново создавать не нужно.

### 5. Лимиты загрузки и сеть

У приложения лимит **на файл**, у nginx `client_max_body_size` — **на тело
одного запроса**. Обычная multipart-загрузка использует `MAX_FILE_SIZE_MB`
(по умолчанию 200 МБ); лимит nginx задавайте с запасом на multipart-разметку,
например `client_max_body_size 201M;`. Для стороннего клиента, передающего
несколько файлов одним запросом, учитывайте их суммарный размер.

Mini App загружает файлы частями через `/api/v1/uploads`: по умолчанию
`UPLOAD_CHUNK_SIZE_MB=8`, а `MAX_CHUNKED_FILE_SIZE_MB=4096` ограничивает
полный размер файла. В nginx и внешнем прокси должен проходить один чанк.
После изменения nginx проверяйте конфигурацию и выполняйте reload.

Cloudflare Free/Pro ограничивает запросы 100 MB, Business — 200 MB; настройка
зоны может быть ниже. Поэтому multipart-запрос на 500 MB не пройдёт только
из-за повышения лимита приложения. Загрузка частями позволяет передать
больший файл, если каждый чанк укладывается в лимиты всех прокси.
Защищённый доступ через tailnet описан отдельно в [TAILSCALE.md](TAILSCALE.md).

При настройке firewall сначала проверьте существующие правила и фактический
порт SSH. Разрешите порт SSH и только порты выбранной схемы (80/443 либо
2083). Порт приложения 8080 оставляйте на localhost. На работающем VPS
обновление бинарника не требует повторного `ufw enable` или замены правил.

### 6. Проверить установку

```bash
sudo systemctl status rust-file-manager.service --no-pager
sudo journalctl -u rust-file-manager.service --no-pager -o cat |
  grep 'starting server' | tail -1
curl --fail --silent --show-error --max-time 20 \
  -o /dev/null -w '%{http_code}\n' https://files.example.com/login
```

В строке запуска ожидаются версия и коммит выбранного выпуска, публичный
`/login` должен вернуть 200. Затем войдите и проверьте футер, зоны файлов,
тестовую загрузку/скачивание и папки бэкапов. Параметр `--version` в бинарнике
не реализован: для версии используйте журнал запуска и футер после входа.

Если вход не работает, проверьте полноту bcrypt-хеша в локальном редакторе
и работу secure-cookie через HTTPS. Пароль не вставляйте в `curl -d` или
командную строку: он попадёт в историю и может быть виден другим процессам.

## Многопользовательский режим

У каждого пользователя есть **личная зона** (видна только ему) и **общая
зона** для обмена файлами между всеми участниками.

## Как пригласить человека

1. Войдите как администратор.
2. В блоке «Пользователи» нажмите **«Создать ссылку-приглашение»**.
3. Отправьте ссылку человеку (мессенджером, почтой — как удобно).
4. Он откроет ссылку, придумает имя и пароль — аккаунт создаётся сразу.

Свойства ссылки:

- **одноразовая** — после регистрации перестаёт действовать;
- **истекает через 7 дней**, если не использована;
- токен — 256 бит случайности, подобрать его нельзя.

## Зоны и права

| Зона | Кто видит | Кто может загружать/удалять |
|---|---|---|
| 🔒 Мои файлы (`home/<имя>/`) | только владелец | только владелец |
| 👥 Общие файлы (`shared/`) | все вошедшие | все вошедшие |

- Доступ к чужой личной зоне невозможен ни по прямой ссылке, ни через
  манипуляции с путём: имя папки берётся из сессии, а не из URL, и каждый
  сегмент пути валидируется.
- Без входа не отдаётся ни один файл (включая общие).
- Администратор управляет пользователями, но через веб-интерфейс чужие личные
  файлы тоже не видит (на сервере они доступны ему как root — это надо
  понимать).

## Управление пользователями

- Список пользователей и кнопка удаления — в блоке «Пользователи» у админа.
- Удаление пользователя **удаляет и его личную папку** со всеми файлами.
- Сессия удалённого пользователя перестаёт действовать немедленно.
- Учётные записи хранятся в `users.json` (`USERS_FILE`), пароли — только в
  виде bcrypt-хешей. Файл стоит включить в бэкап.

## Структура хранилища

```
uploads/
├── shared/              # общая зона
│   ├── Фото/ Документы/ ...
│   └── Бэкапы/
│       ├── Серверы/ HA/ Project/
└── home/
    ├── alice/           # личная зона alice
    │   └── Фото/ Бэкапы/ ...
    └── bob/             # личная зона bob
exchange/                # «Обмен» (с 1.6.0)
└── alice/               # видят только alice и администратор
    ├── from-admin/      # прислал администратор
    └── from-user/       # прислала alice
```

`exchange/` лежит внутри `UPLOAD_DIR`, рядом с `shared/` и `home/`: обычный
бэкап каталога загрузок его включает. При удалении участника его обмен
удаляется вместе с личной зоной.

Обычные категории заполняются автоматически по расширению файла. Раздел
«Бэкапы» (папки Серверы / HA / Project) — только вручную: при загрузке
выберите нужную папку в селекторе «Категория». Папки бэкапов есть и в общей
зоне, и в личной зоне каждого пользователя.

При обновлении со старой (однопользовательской) версии существующие папки
категорий автоматически переносятся в `shared/` при первом старте.

## Без GitHub: своё зеркало или bundle

Если сервер не может скачать код с GitHub, `deploy` и `post_deploy` берут код
файлового менеджера из запасных источников. Порядок такой:

1. GitHub (`RFM_REPO_URL`).
2. Свои зеркала — git-адреса через пробел в `RFM_MIRRORS`: переменная
   окружения или строка в `/etc/rfm-vps.conf`, например
   `RFM_MIRRORS=https://git.example.com/me/rust-file-manager.git`.
3. Bundle с локальной машины: `/var/cache/rfm-vps/rust-file-manager.bundle`.

Если GitHub ответил, берётся его код, даже когда зеркало новее. Если нет —
из запасных берётся старшая версия в `Cargo.toml`. Версию старее работающей
`post_deploy` не ставит, если выпуск не выбран явно через `--ref`. Источник,
откуда взят код, называется в выводе: `код rust-file-manager взят из
источника «зеркало»` (или `«bundle»`). `post_deploy --check` сверяется с ними
же.

**Привезти код с локальной машины** (bundle с веткой `main` и тегами):

```bash
git -C ~/Projects/rust-file-manager bundle create /tmp/rust-file-manager.bundle main --tags
scp /tmp/rust-file-manager.bundle root@203.0.113.10:/tmp/
ssh root@203.0.113.10 'install -d -m 0700 /var/cache/rfm-vps &&
  install -m 0600 /tmp/rust-file-manager.bundle /var/cache/rfm-vps/ && rm /tmp/rust-file-manager.bundle'
ssh -t root@203.0.113.10 /usr/local/sbin/post_deploy
```

На новом сервере команды тоже ставятся с локальной машины:

```bash
scp ~/Projects/rust-file-manager/deploy/rfm-vps.sh root@203.0.113.10:/tmp/
ssh -t root@203.0.113.10 'bash /tmp/rfm-vps.sh setup && /usr/local/sbin/deploy'
```

Bundle используется, только если файл и каталог принадлежат root и
недоступны на запись другим (`0600`/`0700`): код из него собирается и
запускается от root. После обновления bundle можно удалить: старее
установленного он ничего не поставит, но при недоступном GitHub так и будет
источником.

Без интернета не обойтись в таких шагах: `apt-get`, rustup и crates.io при
сборке, Let's Encrypt для certbot. Самообновление команд (`rfm-vps.sh` с
GitHub) без GitHub пропускается с предупреждением. Команды обновятся при
следующем запуске, когда GitHub снова доступен.

## Обновление и переустановка

- Обновление работающего приложения, резервная копия, атомарная
  замена бинарника и откат: [POST_DEPLOY.md](POST_DEPLOY.md).
- Переустановка программы с сохранением данных использует тот же порядок:
  собрать нужный выпуск, установить бинарник, сохранить существующие env,
  `users.json`, uploads, пользователя и службу. Не повторять генерацию
  секретов и создание пустого env.
- Развёртывание с нуля с пустым хранилищем — отдельная операция. Удаление
  текущих пользователей и файлов не является частью обновления.
- Перенос пользователей и файлов на другой VPS —
  [раздел переноса](POST_DEPLOY.md#перенос-на-другой-vps).

## Удалить файловый менеджер — `delete`

```bash
delete --dry-run   # только показать план
delete             # спросить, показать план и удалить после ввода имени сервера
```

**Что делает:**
- останавливает службу;
- выключает сайт nginx `rust-file-manager` (или `-ssl`) и перечитывает nginx;
- переносит в копию `/var/backups/rfm-delete/<дата>-…/files/<прежний путь>`:
  программу, unit, настройки `/etc/rust-file-manager`, данные
  `/var/lib/rust-file-manager` (загруженные файлы и пользователи),
  `/etc/rfm-vps.conf` и сертификат Cloudflare Origin `/etc/nginx/ssl/<домен>`;
- удаляет пользователя `filemgr`.

**Файлы не стираются.** Вернуть файл — `mv` обратно. Удалить копию насовсем —
`rm -rf` с путём из итога. Каталог на другом диске остаётся на месте, команда
об этом пишет.

**В конце — вопросы об общем, которое стало ненужным:**

| Что | По умолчанию | Условие |
|---|---|---|
| Сертификат Let's Encrypt домена | удалить | — |
| Каталог сборки и Rust | удалить | — |
| Swap `/swapfile` | оставить | не выключается, если не хватит памяти |
| nginx и certbot | оставить | спрашивает, только если не осталось ни одного сайта |
| Правила ufw для освободившихся портов | закрыть | SSH не трогает |
| Сами команды | оставить | — |

Другие программы сервера (VPN, Docker, mesh-сеть), sysctl и SSH команда не
трогает.

| Параметр | Что делает |
|---|---|
| `--dry-run` | только показать план |
| `--only fm` | не спрашивать, удалять ли файловый менеджер |
| `--confirm ИМЯ` | не спрашивать имя сервера. Вопросов об общем тогда нет, общее остаётся |

`--yes` команда не принимает: подтверждение — только именем сервера.

На сервере с ботом TelegramOnly команда передаёт управление полной версии
(`tgo-vps delete`). Полная версия заодно отвязывает бота от файлового
менеджера.

## Как команды определяют, что стоит на сервере

| Что | Признак |
|---|---|
| Файловый менеджер установлен | есть `/usr/local/bin/rust-file-manager` или служба `rust-file-manager.service` |
| Его версия и коммит | последняя строка `starting server` в журнале службы |
| Каталог сборки | `/etc/rfm-vps.conf`, иначе `/root/rfm-build` или `/root/rfm-build-*` с репозиторием rust-file-manager |

## Какие файлы создают и используют команды

| Путь | Что это | Секреты |
|---|---|---|
| `/usr/local/sbin/rfm-vps`, `deploy`, `post_deploy` | команды | нет |
| `/etc/rfm-vps.conf` | каталог сборки, ветка или тег, способ HTTPS, `RFM_MIRRORS` | нет |
| `/var/cache/rfm-vps/rust-file-manager.bundle` | код с локальной машины, когда нет GitHub; root, `0700`/`0600` | нет |
| `/root/rfm-build/` | исходники и сборка файлового менеджера | нет |
| `/root/rfm-build.log` | журнал последней сборки | нет |
| `/etc/rust-file-manager/env` | настройки файлового менеджера, права `600` | **да** |
| `/var/backups/rust-file-manager/` | прежние программы и архивы данных; права `700`, по три последних | архивы данных — **да** |
| `/etc/nginx/sites-available/rust-file-manager` или `rust-file-manager-ssl` | сайт nginx (certbot или 2083) | нет |
| `/swapfile` | swap для сборки на маленьком VPS | нет |
| `/run/rfm-vps.lock` | защита от двух одновременных запусков | нет |
| `/var/backups/rfm-delete/` | копии команды `delete`; права `700` | **да** (настройки и данные) |

## Безопасность

- **Секреты создаются на сервере** (`openssl rand`), пишутся в файлы с правами
  `600` и **никогда не выводятся**. На экране только «да/нет» и длины.
- **Пароль администратора** вводится скрыто и хранится только как bcrypt-хеш.
- **Ключ внутреннего API** при проверке передаётся в `curl` через stdin, а не
  аргументом командной строки, поэтому его не видно в списке процессов.
- **Существующие настройки не перезаписываются.** Файл
  `/etc/rust-file-manager/env` создаётся только при первой установке.
- **Обновление команд из репозитория** проверяется: скачанный файл должен
  проходить `bash -n`, иначе остаётся текущая версия.
- **Запасные источники кода** используются, только когда GitHub не ответил;
  bundle с чужим владельцем или правами на запись для других не читается.

## Если что-то не так

| Сообщение или симптом | Что сделать |
|---|---|
| «Команда уже выполняется в другом окне» | дождитесь первой или закройте её; блокировка — `/run/rfm-vps.lock` |
| «Сборка не удалась» и последние строки журнала | читайте `tail -50 /root/rfm-build.log`; прежняя программа не тронута |
| «Новая версия не прошла проверку — возвращаю прежнюю» | сервер снова на прежней версии; причина в `journalctl -u rust-file-manager -n 50` |
| «Порт … занят (…) — файловому менеджеру нужен другой» | это не ошибка: программа встанет на следующий свободный порт, nginx будет вести на него |
| «Порт … занят (…)» и остановка | порт нужен nginx для HTTPS; освободите его или выберите другой `HTTPS_MODE` — чужие службы команда не трогает |
| «на диске свободно … МБ, нужно не меньше …» | сборка не начиналась, программа прежняя; освободите место (`journalctl --vacuum-size=100M`, `apt-get clean`) и запустите команду снова |
| «за время работы команды пропало: …» | названная служба перестала слушать порт; проверьте её (`systemctl --failed`, журнал службы) — сама команда её не останавливает |
| «certbot не выпустил сертификат» | проверьте A-запись домена и запустите `deploy` ещё раз |
| «Нет сертификата Cloudflare» | положите `cert.pem` и `key.pem` в `/etc/nginx/ssl/<домен>/`, затем `deploy` |
| «снаружи … ответил …» | программа работает, но сайт не виден снаружи: DNS, nginx, Cloudflare |
| Фото в Mini App: ошибка 404, в nginx видны `/api/v1/uploads` → 301 и `/api/v1/uploads/` → 404 | выполните `post_deploy --force` с исправленной командой и заново откройте Mini App; обновление исправляет маршрут nginx, API принимает также прежний адрес со слешем |

Повторная установка программ без сброса ОС и настроек:
[DEPLOY_ALGORITHM.md, раздел 6](DEPLOY_ALGORITHM.md#6-повторная-установка-программы-после-исправления).
