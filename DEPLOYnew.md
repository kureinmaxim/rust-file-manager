# Команды `deploy` и `post_deploy`: справочник

Короткая инструкция для оператора или автоматического помощника —
[DEPLOY_ALGORITHM.md](DEPLOY_ALGORITHM.md).

С версии **1.8.0** бот TelegramOnly и файловый менеджер rust-file-manager
ставятся на VPS одной командой и одной командой обновляются:

| Команда | Когда | Что делает |
|---|---|---|
| `deploy` | новый сервер или чего-то не хватает | ставит только недостающее: бота, файловый менеджер, связку между ними |
| `post_deploy` | всё уже стоит | обновляет то, у чего вышла новая версия |
| `rfm-vps status` | в любой момент | показывает, что стоит на сервере (только чтение) |

Обе команды **сами определяют**, что уже установлено. Их можно запускать на
любом сервере: пустом, частично готовом или полностью настроенном.

Скрипт команд — [deploy/rfm-vps.sh](deploy/rfm-vps.sh). Ручной порядок тех же
шагов с пояснениями — [DEPLOYwTELEGRAM.md](DEPLOYwTELEGRAM.md) (установка) и
[POST_DEPLOYwTELEGRAM.md](POST_DEPLOYwTELEGRAM.md) (обновление). Схема сервера —
[ARCHITECTUREwTELEGRAM.md](ARCHITECTUREwTELEGRAM.md).

Все имена и адреса в этом файле — примеры: `files.example.com`,
`files_example_bot`, `203.0.113.10`.

---

## 1. Установить команды на сервер

Один раз на каждом сервере, под root:

```bash
curl -fsSL https://raw.githubusercontent.com/kureinmaxim/rust-file-manager/main/deploy/rfm-vps.sh | bash -s -- setup
```

На минимальном Debian может не быть `curl`. Тогда сначала выполните
`apt-get update && apt-get install -y curl`.

`setup` ставит в `/usr/local/sbin`:
- `rfm-vps` — сам скрипт;
- `deploy`, `post_deploy` и запасное имя `post-deploy` — ссылки на него.

Ожидается сообщение `команды установлены` и короткая подсказка.

**Если хотите сначала прочитать скрипт.** Однострочник выполняет скрипт из
публичного репозитория от root, так же как установщик Docker. Можно сделать
это в три шага:

```bash
curl -fsSLO https://raw.githubusercontent.com/kureinmaxim/rust-file-manager/main/deploy/rfm-vps.sh
less rfm-vps.sh
bash rfm-vps.sh setup
```

**Обновлять команды вручную не нужно.** Перед обычным запуском `deploy` и
`post_deploy` сверяются с репозиторием и при отличии обновляются сами,
сохранив прежний скрипт в `/usr/local/sbin/rfm-vps.backup.*`.
`post_deploy --check` сам скрипт не заменяет. `setup` не перезаписывает
чужую команду с именем `deploy`, `post_deploy` или `post-deploy`.

## 2. `deploy` — установка

```bash
deploy
```

### Порядок работы

1. **Показывает, что стоит на сервере**, и решает, что ставить: всё, чего нет.
2. **Сразу задаёт все вопросы.** После ответов работает без вас, кроме
   запросов при установке бота: токен GitHub (шаг 3), затем `BOT_TOKEN` и ваш
   Telegram ID в установщике бота (шаг 5).
3. **Ставит пакеты:** git, curl, openssl, build-essential, nginx, ufw, socat,
   при certbot — и его. Сразу после этого скачивает код бота, если его нет.
   Репозиторий приватный, поэтому GitHub спросит логин и токен с правом чтения.
   Если доступа нет, установка останавливается здесь, до долгих шагов.
4. **Готовит сервер:**
   - включает обход PMTU (`/etc/sysctl.d/99-tcp-mtu-probing.conf`);
   - создаёт swap 2 ГБ, если его нет, а памяти меньше 3,5 ГБ;
   - включает ufw, если вы согласились.
5. **Ставит бота** (если его нет):
   - ставит Docker;
   - для сети хоста записывает `COMPOSE_FILE` в `.env` бота;
   - запускает установщик бота, который спросит `BOT_TOKEN`, ваш Telegram ID и
     публичный адрес сервера.
6. **Ставит файловый менеджер** (если его нет):
   - ставит Rust;
   - скачивает код в `/root/rfm-build` и собирает в фоне. Ход сборки виден на
     экране раз в 15 секунд, журнал — `/root/rfm-build.log`;
   - создаёт пользователя `filemgr` и каталоги, ставит программу;
   - пишет настройки `/etc/rust-file-manager/env` с паролем и ключами;
   - ставит службу systemd, запускает её и проверяет.
7. **Настраивает nginx и HTTPS** выбранным способом.
8. **Связывает бота с файловым менеджером:**
   - внутренний API и мини-приложение (ID и имя бота берутся у Telegram по
     токену бота);
   - мост socat — только для сети bridge;
   - строки `FILES_*` в `.env` бота;
   - пересоздание бота.
9. **Проверяет всё** и пишет итог и что осталось сделать вручную.

### Сервер, на котором нет ничего

Это обычный случай для `deploy`. От TelegramOnly на сервере заранее ничего не
нужно: ни кода, ни установщика, ни запущенного бота. Команды скачиваются из
публичного репозитория rust-file-manager. `deploy`:
1. ставит git, Docker и остальные пакеты;
2. сам клонирует TelegramOnly в `/opt/TelegramOnly`;
3. запускает установщик бота из этого клона.

Как получить код бота, если вы не хотите вводить токен:
- **SSH-ключ.** Если на сервере есть SSH-ключ с доступом к репозиторию, запустите
  `BOT_REPO_URL=git@github.com:kureinmaxim/TelegramOnly.git deploy`.
- **Код без git.** Если код бота уже доставлен в `/opt/TelegramOnly`, например
  через `rsync` по `DEPLOY.md` бота, `deploy` возьмёт его как есть. Обновлять
  такой код `post_deploy` не сможет: для этого нужен git-клон.

### Вопросы

| Вопрос | Варианты | По умолчанию | Когда спрашивается |
|---|---|---|---|
| Что установить | `both`, `bot`, `fm` | `both` | пустой сервер, интерактивный терминал, без `--only` и `--yes` |
| Сеть Docker для бота | `bridge` — обычная; `host` — если боту нужна mesh-сеть Tailscale/Headscale | `bridge` | если ставится бот |
| Домен файлового менеджера | например `files.example.com`; A-запись должна указывать на сервер | — | если ставится файловый менеджер |
| Способ HTTPS | `certbot` — порт 443 свободен; `cloudflare` — через Cloudflare на 2083; `none` — свой прокси | `certbot`, а если 443 занят — `cloudflare` | если ставится файловый менеджер |
| Почта для Let's Encrypt | адрес или Enter | без почты | при `certbot` |
| Логин администратора сайта | любой | `admin` | если ставится файловый менеджер |
| Пароль администратора | от 8 символов, дважды, ввод не виден | — | если ещё нет настроек файлового менеджера |
| Включить ufw | да или нет | да | если ufw выключен |
| Начинаем? | да или нет | да | всегда, после показа плана |

Неверный домен, короткий или несовпавший пароль переспрашиваются.

**Порт SSH для ufw** берётся из текущего подключения. Если его не видно,
например в консоли провайдера, а не по SSH, ufw не включается, чтобы не
потерять доступ.

### Что остаётся сделать вручную

Это требует вашего Telegram, поэтому `deploy` выводит готовые шаги с вашим
доменом и именем бота:
1. **@BotFather** → `/mybots` → бот → **Bot Settings → Configure Mini App →
   Enable Mini App** → `https://files.example.com/tg/`.
2. Откройте `https://t.me/files_example_bot?startapp` и войдите логином
   администратора. Так ваш Telegram станет администратором файлов.
3. В боте: `/version` и `/files_status`.

Для HTTPS через Cloudflare нужен ещё **Origin-сертификат**: положите
`cert.pem` и `key.pem` в `/etc/nginx/ssl/files.example.com/` и запустите
`deploy` ещё раз (подробно — [DEPLOYwTELEGRAM.md](DEPLOYwTELEGRAM.md) §2.7Б).
Затем в Cloudflare:
- режим SSL/TLS **Full (strict)**;
- Origin Rule на порт 2083;
- Bypass cache для `/api/*` и `/d/*`.

### Частичная установка и повторный запуск

- **Только бот:** `deploy --only bot`. Позже обычный `deploy` доставит файловый
  менеджер и сразу свяжет его с ботом.
- **Только файловый менеджер:** `deploy --only fm`. Позже `deploy` доставит бота
  и свяжет их.
- **Повторный `deploy` безопасен.** Он ничего не переустанавливает и не меняет
  существующие настройки, а только доделывает отложенное:
  - nginx на 2083 после того, как положили сертификат Cloudflare;
  - сертификат Let's Encrypt, если DNS в прошлый раз ещё не обновился;
  - ключ бота, если он разошёлся с ключом файлового менеджера.
- **Если оборвался SSH**, запустите `deploy` снова: сборка продолжается в
  фоне, и команда её дождётся.

### Без вопросов

Ответы можно задать переменными окружения и добавить `--yes`. Пароль
спрашивается всё равно:

```bash
RFM_DOMAIN=files.example.com HTTPS_MODE=certbot LE_EMAIL=admin@example.com \
BOT_NETWORK=bridge ENABLE_UFW=yes deploy --yes
```

| Переменная | Значения |
|---|---|
| `RFM_DOMAIN` | домен файлового менеджера |
| `HTTPS_MODE` | `certbot`, `cloudflare`, `none` |
| `LE_EMAIL` | почта для Let's Encrypt |
| `RFM_ADMIN_LOGIN` | логин администратора, по умолчанию `admin` |
| `BOT_NETWORK` | `bridge`, `host` |
| `ENABLE_UFW` | `yes`, `no` |
| `BOT_REPO_URL` | откуда скачать бота; по умолчанию GitHub по HTTPS (спросит токен), можно `git@github.com:kureinmaxim/TelegramOnly.git` для SSH-ключа |

## 3. `post_deploy` — обновление

```bash
post_deploy
```

### Порядок работы

1. **Показывает, что стоит на сервере.** Если нет ни бота, ни файлового
   менеджера, предлагает `deploy` и завершается. В терминале уточняет,
   что обновить (`both`, `bot`, `fm`), нужен ли архив данных FM (по умолчанию
   нет), показывает план и спрашивает подтверждение. `--yes` убирает эти
   вопросы; запуск через stdin сохраняет прежнее неинтерактивное поведение.
2. **Обновляет файловый менеджер** из `main` (или из закреплённого тега):
   - если на сервере уже этот коммит и служба работает, ничего не делает;
   - иначе собирает в фоне в прежнем каталоге сборки. Зависимости там уже
     скомпилированы, поэтому сборка занимает несколько минут;
   - сохраняет прежнюю программу в `/var/backups/rust-file-manager/`;
   - атомарно заменяет программу и перезапускает службу;
   - проверяет, что запущен именно новый коммит, а сайт, мини-приложение и API
     для бота отвечают;
   - **если проверки не прошли, сам возвращает прежнюю версию** и сообщает об
     этом. Обновление зависимого бота в этом запуске откладывается.
3. **Обновляет бота:**
   - если бот запущен в сети хоста, а `COMPOSE_FILE` в `.env` нет, сначала
     записывает его. Иначе пересборка выбила бы бота из mesh-сети;
   - `git pull` и `scripts/rebuild_bot.sh`, затем сверяет версию в контейнере с
     репозиторием;
   - для бота через systemd: `git pull`, при изменившихся зависимостях
     `pip install`, перезапуск службы;
   - если в `/opt/TelegramOnly` есть свои правки или коммиты, бота не трогает
     и пишет об этом.
4. **Проверяет связку** и чинит её, если ключи разошлись.
5. **Убирает старое:** держит три последние копии программы и `.env`.
6. **Пишет итог:** что обновлено, с какой версии на какую.

Сначала обновляется файловый менеджер, потом бот: новые функции бота опираются
на API файлового менеджера, а две сборки одновременно на маленьком VPS могут
подвесить SSH.

### Параметры

| Команда | Что делает |
|---|---|
| `post_deploy` | обновить всё, что устарело |
| `post_deploy --check` | показать обновления без замены программ, env и команд; Git-метаданные бота обновляются через fetch |
| `post_deploy --only fm` | только файловый менеджер |
| `post_deploy --only bot` | только бот |
| `post_deploy --ref v1.8.0` | поставить выпуск по тегу и **остаться на нём**; следующие запуски тоже возьмут v1.8.0 |
| `post_deploy --ref main` | вернуться к последней версии из `main` |
| `post_deploy --force` | пересобрать и перезапустить, даже если версия та же |
| `post_deploy --backup-data` | перед заменой программы сохранить ещё и архив данных; служба на это время останавливается |
| `post_deploy --yes` | согласованное обновление без вопросов выбора и подтверждения |

`--only` также исключает настройку связки и перезапуск второго проекта.
После отдельных обновлений связку можно проверить обычным `deploy`.
Отсутствующий выбранный проект и код бота без git дают ошибку с подсказкой,
а не успешный итог пропущенного обновления. Ошибки nginx и пересоздания
бота после изменения связки возвращаются как ненулевой код выхода.

Код завершения `0` значит, что всё обновлено или уже актуально. `1` значит, что
что-то не удалось: подробности в итоге.

### Первый запуск на сервере, установленном до 1.8.0

Достаточно поставить команды (раздел 1) и выполнить `post_deploy`. Команда
найдёт:
- прежний каталог сборки `/root/rfm-build…` по его git-репозиторию;
- домен — по настройкам файлового менеджера;
- сеть бота — по контейнеру.

## 4. `rfm-vps status`

Только чтение. Показывает:
- **файловый менеджер:** версию и коммит, состояние службы, адрес сайта,
  включены ли мини-приложение и API для бота, каталог сборки;
- **бота:** способ запуска (Docker или systemd), версию, сеть и связан ли он с
  файловым менеджером.

---

## 5. Как команды определяют, что стоит на сервере

| Что | Признак |
|---|---|
| Файловый менеджер установлен | есть `/usr/local/bin/rust-file-manager` или служба `rust-file-manager.service` |
| Его версия и коммит | последняя строка `starting server` в журнале службы |
| Бот в Docker | есть контейнер `telegram-helper-lite` |
| Бот через systemd | есть служба `telegramonly.service` |
| Код бота скачан, но бот не установлен | есть `/opt/TelegramOnly/.git` без контейнера и службы |
| Сеть бота | `docker inspect` контейнера: `host` или имя сети bridge |
| Бот связан с файловым менеджером | в `.env` бота есть `FILES_SERVICE_TOKEN` и `FILES_INTERNAL_URL` |
| Каталог сборки | `/etc/rfm-vps.conf`, иначе `/root/rfm-build` или `/root/rfm-build-*` с репозиторием rust-file-manager |

## 6. Какие файлы создают и используют команды

| Путь | Что это | Секреты |
|---|---|---|
| `/usr/local/sbin/rfm-vps`, `deploy`, `post_deploy` | команды | нет |
| `/etc/rfm-vps.conf` | каталог сборки, ветка или тег, способ HTTPS | нет |
| `/root/rfm-build/` | исходники и сборка файлового менеджера | нет |
| `/root/rfm-build.log` | журнал последней сборки | нет |
| `/etc/rust-file-manager/env` | настройки файлового менеджера, права `600` | **да** |
| `/opt/TelegramOnly/.env` | настройки бота, права `600` | **да** |
| `/var/backups/rust-file-manager/` | прежние программы, копии `env`, архивы данных; права `700`, по три последних | копии `env` — **да** |
| `/var/backups/telegramonly/` | копии `.env` бота перед правками; права `700`, три последние | **да** |
| `/etc/systemd/system/rfm-internal-bridge.service` | мост socat, только для сети bridge | нет |
| `/etc/nginx/sites-available/rust-file-manager` или `rust-file-manager-ssl` | сайт nginx (certbot или 2083) | нет |
| `/etc/sysctl.d/99-tcp-mtu-probing.conf`, `/swapfile` | обход PMTU и swap | нет |
| `/run/rfm-vps.lock` | защита от двух одновременных запусков | нет |

## 7. Безопасность

- **Секреты создаются на сервере** (`openssl rand`), пишутся в файлы с правами
  `600` и **никогда не выводятся**. На экране только «да/нет» и длины.
- **Пароль администратора** вводится скрыто и хранится только как bcrypt-хеш.
- **Токен бота и ключ внутреннего API** передаются в `curl` через stdin, а не
  аргументами командной строки, поэтому их не видно в списке процессов.
- **Внутренний API** слушает только `127.0.0.1:8091`. Для сети bridge мост и
  правило ufw открывают его только docker-сети бота.
- **Существующие настройки не перезаписываются.** Команды дописывают только
  недостающие строки. Единственная замена — ключ в `.env` бота, если он
  разошёлся с ключом файлового менеджера. Перед любой правкой сохраняется копия
  файла.
- **Обновление команд из репозитория** проверяется: скачанный файл должен
  проходить `bash -n`, иначе остаётся текущая версия.

## 8. Если что-то не так

| Сообщение или симптом | Что сделать |
|---|---|
| «Команда уже выполняется в другом окне» | дождитесь первой или закройте её; блокировка — `/run/rfm-vps.lock` |
| GitHub спрашивает логин и пароль | репозиторий бота приватный: логин GitHub и токен на чтение вместо пароля |
| «Не удалось скачать TelegramOnly» | неверный токен или нет доступа; с SSH-ключом: `BOT_REPO_URL=git@github.com:kureinmaxim/TelegramOnly.git deploy` |
| «Каталог /opt/TelegramOnly не пустой, но это не код бота» | посмотрите, что там лежит, перенесите или удалите сами и запустите `deploy` снова |
| «Сборка не удалась» и последние строки журнала | читайте `tail -50 /root/rfm-build.log`; прежняя программа не тронута |
| «Новая версия не прошла проверку — возвращаю прежнюю» | сервер снова на прежней версии; причина в `journalctl -u rust-file-manager -n 50` |
| «certbot не выпустил сертификат» | проверьте A-запись домена и запустите `deploy` ещё раз |
| «Нет сертификата Cloudflare» | положите `cert.pem` и `key.pem` в `/etc/nginx/ssl/<домен>/`, затем `deploy` |
| «Не удалось узнать ID бота» | проверьте `BOT_TOKEN` в `/opt/TelegramOnly/.env`, затем `deploy` |
| «В /opt/TelegramOnly изменены файлы» или «свои коммиты» | сохраните или уберите локальные правки бота; `post_deploy --only fm` обновит только файловый менеджер |
| «снаружи … ответил …» | программа работает, но сайт не виден снаружи: DNS, nginx, Cloudflare |
| Нет кнопки «Файлы» в Telegram | перезапустите Telegram; проверьте `/files_status` и что вы вошли в мини-приложение (раздел 2) |

## 9. Проверка самих команд

Тесты запускаются в песочнице и не трогают систему. systemd, Docker, apt, ufw,
nginx, certbot, curl и сборка подменены заглушками, GitHub — локальными
репозиториями. Нужен root:

```bash
bash deploy/tests/rfm-vps.test.sh
```

Ожидается `Пройдено: 113, ошибок: 0`. Проверяются:
- пустой сервер, в том числе без доступа к репозиторию бота и с кодом бота,
  доставленным без git;
- установка с нуля в обеих сетях и обоими способами HTTPS;
- установка по частям и повторный `deploy`;
- обновление с откатом и неудачная сборка;
- закрепление сети хоста, исправление ключа, `--ref`;
- самообновление команд;
- ответы на вопросы вручную;
- что секреты не попадают ни в вывод, ни в аргументы команд.
