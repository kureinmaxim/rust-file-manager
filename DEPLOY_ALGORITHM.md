# Установка и обновление rust-file-manager: простой алгоритм

Для оператора и автоматического помощника. Команды выполняются на нужном VPS
с Debian/Ubuntu и systemd, под root. `deploy` устанавливает файловый менеджер,
nginx и HTTPS; `post_deploy` обновляет установленный файловый менеджер.
Другие программы на сервере (Docker-контейнеры, VPN, ботов) команды не ставят
и не трогают.

Алгоритм для помощника:

1. Уточнить VPS и домен.
2. Проверить статус, реальные пути и занятые порты.
3. Выбрать `deploy` для установки или `post_deploy` для обновления.
4. Задать нужные вопросы, показать план и получить подтверждение.
5. Выполнить; при ошибке остановиться и не продолжать зависимые шаги.
6. Проверить код выхода, версию, службу и HTTPS.
7. Сообщить результат и конкретные оставшиеся ручные действия.

## 1. Один раз поставить команды

На совсем пустом сервере сначала нужен curl:

```bash
sudo -i
apt-get update && apt-get install -y curl ca-certificates
curl -fsSL https://raw.githubusercontent.com/kureinmaxim/rust-file-manager/main/deploy/rfm-vps.sh | bash -s -- setup
rfm-vps status
```

Обычные запуски сверяют команды с выбранной веткой или тегом GitHub.
Для проверки отдельной рабочей версии можно установить исходный файл через
`bash /путь/к/rfm-vps.sh setup`; чтобы он не заменился опубликованной версией,
запускайте этот исходный файл напрямую.

## 2. Определить состояние и выбрать действие

| Что уже установлено | `deploy` | `post_deploy` |
|---|---|---|
| Ничего | поставить файловый менеджер, nginx и HTTPS | отказ и подсказка запустить `deploy` |
| Файловый менеджер | доделать отложенное: сертификат, nginx на 2083 | обновить программу с проверкой и откатом |

**Код на диске ещё не означает установленный сервис.** Остановленную
установленную службу `post_deploy` перезапустит, даже если коммит не
изменился. При оборванной установке с отсутствующим env/юнитом или
нестандартном расположении помощник останавливается, показывает недостающее
и предлагает отдельный план восстановления; не заменяет рабочие данные.

## 3. Задать только нужные вопросы

**Для `deploy`:**

1. Домен, HTTPS (`certbot`, `cloudflare`, `none`), логин и пароль
   администратора. `certbot` требует свободного 443 или уже согласованного
   nginx; Cloudflare использует 2083; `none` означает свой HTTPS-прокси.
   Занятые 8080/8091 или порт HTTPS команда показывает до установки и сборки.
2. Включать ли ufw? Команда сохраняет текущий SSH-порт. Если уже слушают
   другие службы, она по умолчанию и при `--yes` ufw не включает; при
   согласии сначала разрешает все слушающие сейчас порты.
3. Показать план и получить подтверждение.

**Для `post_deploy`:**

1. Выполнить `post_deploy --check`: узнать обновление без замены программы,
   env, команд и перезапусков.
2. Делать архив данных? Это требует свободного места и короткой остановки.
3. Показать план и подтвердить обновление. По умолчанию используется `main`,
   либо уже закреплённый выпуск (`--ref`).

## 4. Выполнить последовательно

**Установка:** вопросы → план → проверка портов → пакеты → swap и ufw →
сборка и установка → HTTPS → проверки → оставшиеся ручные действия.

**Обновление:** статус → проверка версии → вопросы и план → swap при нехватке
памяти → сборка без остановки старой программы → копия старой программы →
замена и проверка → маршрут загрузок в nginx. Сбой проверки откатывает
программу; сбой сборки не заменяет старую.

Если запрошенный архив данных не создан, программа не заменяется.
На VPS с памятью меньше 3,5 ГБ без swap перед сборкой создаётся swap 2 ГБ
(при свободных 3 ГБ на диске).

Автоматический запуск после заранее согласованного выбора:

```bash
RFM_DOMAIN=files.example.com HTTPS_MODE=certbot ENABLE_UFW=no deploy --yes
post_deploy --yes
post_deploy --backup-data --yes
```

`--yes` убирает вопросы выбора и подтверждения, но пароль администратора при
первой установке спрашивается всё равно. Параметры не вводятся заново, если
они уже заданы. При EOF на обязательном вопросе команда завершается с ошибкой.

## 5. Проверить результат и остановиться при ошибке

Код выхода `0` означает успешные локальные проверки; ненулевой код — ошибку
или отмену. Отдельно проверить публичный HTTPS: вход, загрузку и скачивание.
Отложенный DNS или сертификат Cloudflare — ещё не готовая внешняя установка,
даже если локальные проверки завершились с кодом `0`.

Параметры установки — [DEPLOY.md](DEPLOY.md), обновления — [POST_DEPLOY.md](POST_DEPLOY.md).

## 6. Повторная установка программы после исправления

Для установленного сервера используйте `post_deploy --force`. Эта команда
пересобирает программу, сохраняя пользователей, пароли, файлы, домен и
сертификат. Архив данных по умолчанию выключен; копия прежней программы для
отката сохраняется автоматически.

```bash
curl -fsSL https://raw.githubusercontent.com/kureinmaxim/rust-file-manager/main/deploy/rfm-vps.sh | bash -s -- setup
```

Следующую команду вводите отдельно, чтобы её текст не попал в ответы на вопросы:

```bash
post_deploy --force
```

Обновление проверяет и применяет маршрут загрузок в активных сайтах
`rust-file-manager` и `rust-file-manager-ssl`. Прежний `location /api/v1/uploads/`
исправляется без замены остальной конфигурации; даже ручная правка применяется
через `nginx -t` и reload. При ошибке проверки или reload изменённые строки
возвращаются и команда сообщает об ошибке. `--check` и режим собственного
прокси `HTTPS_MODE=none` nginx не изменяют.

После обновления закройте Mini App и откройте снова, затем загрузите фото.
Старый nginx мог сохранить в клиенте редирект с `/api/v1/uploads` на
`/api/v1/uploads/`; API принимает оба адреса с той же проверкой доступа.
