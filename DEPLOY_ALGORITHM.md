# Установка и обновление двух проектов: простой алгоритм

Для оператора и автоматического помощника. Проверено 09.10.2026 на коде
TelegramOnly **3.26.0** и rust-file-manager **1.9.0** с исправлениями команд.
Команды выполняются на нужном VPS с Debian/Ubuntu и systemd, под root.
`deploy` устанавливает недостающее; `post_deploy` обновляет установленное.

Алгоритм для помощника:

1. Уточнить VPS и результат: оба проекта, бот или файлы.
2. Проверить статус, реальные пути, способ запуска и занятые порты.
3. Выбрать `deploy` для недостающего или `post_deploy` для установленного.
4. Задать нужные вопросы, показать план и получить подтверждение.
5. Выполнить шаги последовательно; при ошибке остановить зависимые шаги.
6. Проверить код выхода, версии, службы, HTTPS и связку в Telegram.
7. Сообщить результат и конкретные оставшиеся ручные действия.

## 1. Один раз поставить команды

На совсем пустом сервере сначала нужен curl:

```bash
sudo -i
apt-get update && apt-get install -y curl ca-certificates
curl -fsSL https://raw.githubusercontent.com/kureinmaxim/rust-file-manager/main/deploy/rfm-vps.sh | bash -s -- setup
rfm-vps status
```

Обычные запуски сверяют команды с выбранной веткой или тегом GitHub.
Для проверки отдельной рабочей версии можно установить исходный файл через
`bash /путь/к/rfm-vps.sh setup`; чтобы он не заменился опубликованной версией,
запускайте этот исходный файл напрямую.

## 2. Определить состояние и выбрать действие

Помощник сначала уточняет **какой VPS** и **что нужно в результате: оба
проекта, только бот или только файловый менеджер**. Затем читает статус,
способ запуска, реальные пути и занятые порты, не выводя секреты.

| Что уже установлено | `deploy` для обоих проектов | `post_deploy` |
|---|---|---|
| Ничего | поставить оба, настроить связку | отказ и подсказка запустить `deploy` |
| Только TelegramOnly | добавить файловый менеджер и связку | обновить только бота |
| Только rust-file-manager | добавить бота и связку | обновить только файловый менеджер |
| Оба | проверить связку, доделать отложенную настройку | обновить FM, затем бота |

Для одного проекта: `deploy --only bot` или `deploy --only fm`.
При обновлении `post_deploy --only bot|fm` не меняет настройки и не
перезапускает второй проект. Для последующей настройки связки — обычный
`deploy`.

**Код на диске ещё не означает установленный сервис.** Существующий git-клон
бота без контейнера/службы используется при установке. Код, доставленный
без git, можно установить; обновлять его нужно прежним способом доставки.
Остановленную установленную службу FM `post_deploy` перезапустит, даже если
коммит не изменился. При оборванной установке с отсутствующим env/юнитом или
нестандартном расположении помощник останавливается, показывает недостающее
и предлагает отдельный план восстановления; не заменяет рабочие данные.

## 3. Задать только нужные вопросы

**Для `deploy`:**

1. На пустом VPS: оба проекта, бот или файлы? В терминале это спрашивает
   команда; при частичной установке она предлагает недостающее в плане.
2. Для нового бота: `bridge` или `host`? `host` нужен, если бот использует
   mesh-сеть. Нужен доступ к приватному репозиторию: SSH-ключ или запрос
   GitHub на логин/токен. Токен не записывать в URL или текст команды.
3. Для нового FM: домен, HTTPS (`certbot`, `cloudflare`, `none`), логин и
   пароль администратора. `certbot` требует свободного 443 или уже
   согласованного nginx; Cloudflare использует 2083; `none` означает свой
   HTTPS-прокси. Если DNS, порт или прокси не согласованы, помощник сначала
   уточняет их, не останавливая посторонние сервисы.
4. Включать ли ufw? Команда сохраняет текущий SSH-порт. Помощник дополнительно
   проверяет, что существующие нужные порты разрешены; не включает новый
   файрвол вслепую на рабочем VPN-сервере.
5. Показать план и получить подтверждение. Установщик бота отдельно спросит
   BOT_TOKEN (скрыто), Telegram ID администратора и публичный адрес.

**Для `post_deploy`:**

1. Выполнить `post_deploy --check`: узнать обновления без замены программ,
   env, команд и перезапусков. Git-метаданные бота могут обновиться через fetch.
2. В терминале: оба проекта или один? Если установлен один — выбор очевиден.
3. Делать архив данных FM? Это требует свободного места и короткой остановки.
4. Показать план и подтвердить обновление. По умолчанию используется `main`,
   либо уже закреплённый выпуск FM. Переход с экспериментальной ветки бота,
   локальные коммиты и переписанную историю не исправлять через `reset --hard`.

## 4. Выполнить последовательно

**Установка:** вопросы → план → доступ к коду → пакеты и подготовка → бот →
FM → HTTPS → связка → проверки → оставшиеся ручные действия.

**Обновление:** статус → проверка версии → вопросы и план → сборка FM без
остановки старого → копия старой программы → замена и проверка → бот →
проверка связки. Сбой FM откатывает программу и откладывает обновление бота.
Сбой сборки не заменяет старую программу. Автоматического отката образа
бота и миграций данных команда не обещает.

Если запрошенный архив данных не создан, программа не заменяется.
Если зависимости systemd-бота не установлены, он не перезапускается;
после исправления причины повторить `post_deploy --only bot --force`.

Помощник сохраняет резервную копию перед изменением существующего файла,
не печатает `.env`, ключи и журналы с секретами, не делает `compose down`,
не меняет VPN, mesh-сеть и прочие проекты. Архивы данных и секретов остаются
на сервере в закрытых каталогах, вне Git.

## 5. Автоматический и полуавтоматический режимы

Самый простой полуавтоматический запуск:

```bash
deploy
# На уже установленном сервере:
post_deploy --check
post_deploy
```

Автоматическое обновление после заранее согласованного выбора:

```bash
post_deploy --yes
post_deploy --only fm --backup-data --yes
post_deploy --only bot --yes
```

`--yes` убирает вопросы выбора и подтверждения, но **не создаёт доступ к
GitHub, пароль или токен бота**. Для полностью автоматической установки
должны быть заранее подготовлены Git-доступ, закрытые настройки и способ
передачи нового пароля через stdin из хранилища секретов. Без них помощник
переходит к интерактивному вводу. Пример без секретов в строке команды:

```bash
RFM_DOMAIN=files.example.com HTTPS_MODE=certbot \
BOT_NETWORK=bridge ENABLE_UFW=no deploy --yes
```

Параметры не вводятся заново, если они уже заданы. При EOF на обязательном
вопросе команда завершается с ошибкой. Нет бесконечного ожидания пароля.

## 6. Проверить результат и остановиться при ошибке

Код выхода `0` означает успешные локальные проверки; ненулевой код — ошибку
или отмену. Помощник проверяет код выхода, реальные версии и статус служб.
При ошибке не продолжает зависимые шаги и сообщает, что сохранено/откачено.
Повторный запуск не должен переустанавливать рабочие компоненты.

Отдельно проверить публичный HTTPS и в Telegram `/version`, `/files_status`,
кнопку «Файлы», вход, загрузку и уведомление. После первой установки включить
Mini App в @BotFather по адресу, который напечатала команда. Отложенный DNS,
сертификат Cloudflare или шаг BotFather — ещё не готовая внешняя установка,
даже если локальные проверки завершились с кодом `0`.
