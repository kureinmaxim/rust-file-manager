# Схема: бот TelegramOnly и rust-file-manager на одном VPS

Справочник отвечает на четыре вопроса:
- что установлено на сервере;
- как бот, файловый менеджер, Telegram и браузер обмениваются командами;
- где на диске лежат общие файлы, личные файлы и файлы «Обмена»;
- где хранятся секреты.

Другие справочники этой серии:
- установка с нуля — [DEPLOYwTELEGRAM.md](DEPLOYwTELEGRAM.md);
- обновление работающего сервера — [POST_DEPLOYwTELEGRAM.md](POST_DEPLOYwTELEGRAM.md).

Схема описывает rust-file-manager **1.7.0** и TelegramOnly **3.25.0**. Все
имена, адреса и логины здесь — примеры: `files.example.com`,
`files_example_bot`, участники `anna` и `bob`.

## 1. Общая картина

```
                    ИНТЕРНЕТ
  ┌──────────────────────┐        ┌───────────────────────────────┐
  │ Telegram (облако)    │        │ Браузер; Telegram на телефоне │
  │ api.telegram.org     │        │ открывает мини-приложение     │
  └──────────▲───────────┘        └───────────────┬───────────────┘
             │ бот сам забирает                   │ HTTPS: files.example.com
             │ сообщения (long polling)           │ (через Cloudflare или напрямую)
═════════════╪════════════════════════════════════╪══════════════ VPS ═══════
             │                                    ▼
  ┌──────────┴─────────────────┐      ┌───────────────────────┐
  │ Бот TelegramOnly           │      │ nginx :443 или :2083  │
  │ Docker: telegram-helper-   │      └───────────┬───────────┘
  │ lite, /opt/TelegramOnly    │                  │ http://127.0.0.1:8080
  │                            │      ┌───────────▼───────────────────────┐
  │ /files, /files_status,     │      │ rust-file-manager                 │
  │ /files_invite, /files_bind │      │ systemd, пользователь filemgr     │
  │ кнопка «Файлы»             │      │                                   │
  │ уведомления об «Обмене»    │      │ :8080 сайт, мини-приложение /tg/, │
  │                            │─────▶│       API /api/v1, ссылки /d/     │
  └────────────────────────────┘      │ :8091 внутренний API для бота     │
     http://127.0.0.1:8091            └───────────┬───────────────────────┘
     (или через мост socat,                       │ чтение и запись
      если бот в сети bridge)                     ▼
     + служебный токен                ┌──────────────────────────────────┐
                                      │ /var/lib/rust-file-manager/      │
                                      │   users.json                     │
                                      │   uploads/shared/   — общие      │
                                      │   uploads/home/     — личные     │
                                      │   uploads/exchange/ — «Обмен»    │
                                      └──────────────────────────────────┘
```

Главные правила связки:
- **Направление одно: бот → файловый менеджер.** Файловый менеджер никогда не
  обращается ни к боту, ни к Telegram и не знает токен бота.
- **Внутренний API (порт 8091) слушает только локальный адрес** и пускает
  только со служебным токеном. nginx его наружу не отдаёт.
- **Файлы хранит только файловый менеджер.** Бот файлов не хранит и не
  пересылает: он открывает мини-приложение и пишет уведомления.

## 2. Что где установлено

| Часть | Как запущена | Программа и код | Настройки | Данные | Журнал |
|---|---|---|---|---|---|
| rust-file-manager | служба systemd `rust-file-manager.service`, пользователь `filemgr` | `/usr/local/bin/rust-file-manager`; веб-страницы и мини-приложение вшиты в программу | `/etc/rust-file-manager/env` (root, `600`) | `/var/lib/rust-file-manager/` | `journalctl -u rust-file-manager` |
| Бот TelegramOnly | Docker, сервис compose `telegram-helper`, контейнер `telegram-helper-lite` | `/opt/TelegramOnly` (код и образ Docker) | `/opt/TelegramOnly/.env` (`600`) | `/opt/TelegramOnly/*.json` — данные самого бота, не файлы | `docker logs telegram-helper-lite` |
| nginx | служба systemd `nginx` | системный пакет | `/etc/nginx/sites-available/…`, сертификаты в `/etc/nginx/ssl/` или `/etc/letsencrypt/` | — | `/var/log/nginx/` |
| Мост socat (только если бот в сети bridge) | служба `rfm-internal-bridge` | `/usr/bin/socat` | `/etc/systemd/system/rfm-internal-bridge.service` | — | `journalctl -u rfm-internal-bridge` |
| Сборка файлового менеджера | не работает постоянно | `/root/rfm-build` (исходники и `target/`) | — | — | `/root/rfm-build.log` |
| Резервные копии | — | — | — | `/var/backups/rust-file-manager/` | — |

Для работы файлового менеджера каталог сборки не нужен: он нужен только для
следующего обновления.

## 3. Адреса и порты

| Адрес | Кто слушает | Кто может подключиться |
|---|---|---|
| `:443` или `:2083` | nginx | интернет: браузеры, Telegram, Cloudflare |
| `127.0.0.1:8080` | rust-file-manager: сайт, мини-приложение, API | только nginx |
| `127.0.0.1:8091` | rust-file-manager: внутренний API | только бот, по служебному токену |
| `172.18.0.1:8091` | мост socat, только для бота в сети bridge | только docker-сеть бота (правило ufw) |
| `:8000` | REST API бота | в сети bridge слушает только `127.0.0.1`; в сети хоста — все адреса, наружу его закрывает ufw |

**Как бот видит порт 8091:**
- **сеть хоста** (`compose.host.yaml`): бот делит сеть с сервером и ходит
  напрямую на `http://127.0.0.1:8091`;
- **сеть bridge**: для контейнера `127.0.0.1` — это сам контейнер. Поэтому бот
  ходит на шлюз docker-сети `http://172.18.0.1:8091`, а мост socat пересылает
  запрос на `127.0.0.1:8091` сервера.

## 4. Как проходят команды

### 4.1. Браузер → сайт

```
Браузер ──HTTPS──▶ nginx ──▶ :8080  /login (логин + пароль) → cookie сеанса на 12 часов
                                    /                        → «Мои», «Общие», «Обмен»
                                    /register?token=…        → регистрация по приглашению
```

- Пароли хранятся только как bcrypt-хеши: администратора — в
  `/etc/rust-file-manager/env`, участников — в `users.json`.
- Cookie подписана ключом из `SESSION_SECRET`. На сервере сеансы не хранятся.

### 4.2. Мини-приложение в Telegram

```
Кнопка «Файлы» или ссылка t.me/files_example_bot?startapp
        │
        ▼
Telegram открывает https://files.example.com/tg/ ──▶ nginx ──▶ :8080
        │
        │ 1. POST /api/v1/tg/session  + initData (данные Telegram с его подписью)
        ▼
rust-file-manager проверяет подпись Telegram (Ed25519) по числовому ID бота.
Токен бота для этого не нужен.
        │
        ├─ Telegram уже привязан   → токен доступа на 12 часов (хранится только в памяти страницы)
        └─ ещё не привязан         → экран привязки:
                                     POST /api/v1/tg/link      логин + пароль (5 попыток за 15 минут)
                                     POST /api/v1/tg/register  по приглашению inv_…
        │
        │ 2. Дальше все запросы с токеном:
        ▼
GET  /api/v1/overview, /api/v1/files       списки, поиск, место на диске
POST /api/v1/folders                       новая папка
POST /api/v1/uploads → PUT …/{id} (части по 8 МБ) → POST …/{id}/complete
                                           загрузка с докачкой
GET  /api/v1/exchange, /api/v1/exchange/{участник}
                                           «Обмен»
POST /api/v1/files/{id}/link  → ссылка /d/<токен>
                                           скачивание и просмотр
```

**Ссылки на скачивание `/d/<токен>`** подписаны и привязаны к одному файлу.
Для скачивания ссылка живёт 5 минут, для просмотра и видео — 6 часов. Перед
скачиванием Telegram запрашивает размер файла отдельным запросом HEAD, поэтому
ссылка отвечает и на него. nginx не пишет эти ссылки в журнал: в пути лежит
токен.

### 4.3. Бот → файловый менеджер (внутренний API)

Каждый запрос бота идёт с заголовком
`Authorization: Bearer <FILES_SERVICE_TOKEN>`. Это тот же секрет, что
`INTERNAL_API_TOKEN` у файлового менеджера.

| Когда | Что делает бот | Запрос к файловому менеджеру |
|---|---|---|
| `/files_status` (администратор) | версия, диск, число участников и привязок | `GET /internal/v1/health`, `GET /internal/v1/status` |
| `/files` | показывает кнопку мини-приложения и проверяет привязку | `GET /internal/v1/resolve?telegram_id=…` |
| Раз в 10 минут (`FILES_MENU_SYNC_MINUTES`) | ставит кнопку «Файлы» привязанным и убирает у отвязанных | `GET /internal/v1/tg-links` |
| `/files_invite` (администратор файлов) | создаёт одноразовое приглашение на 7 дней | `POST /internal/v1/invites` |
| `/files_bind <tg_id> <логин>` или `… off` | привязывает или отвязывает Telegram вручную (запасной путь) | `POST /internal/v1/bind`, `POST /internal/v1/unbind` |
| Раз в 10 минут (`FILES_NOTIFY_MINUTES`) | забирает новые файлы в «Обмене» и пишет получателям | `GET /internal/v1/events?after=<id>` |

Приглашения и привязки выдаются, только если Telegram того, кто пишет боту,
привязан к администратору файлового менеджера. Это проверяет **сам файловый
менеджер** по привязкам в `users.json`, а не только бот по своему списку
`ADMIN_USER_IDS`.

### 4.4. Бот → Telegram

- **Сообщения.** Бот забирает их сам (long polling), входящих подключений к
  нему нет.
- **Кнопка «Файлы».** Привязанным пользователям бот ставит слева от поля ввода
  кнопку мини-приложения (`setChatMenuButton`). Подсказки команд по «/» при
  этом остаются.
- **Уведомления об «Обмене».** Бот отправляет сообщение с кнопкой
  «📂 Открыть обмен». Кнопка открывает мини-приложение сразу на «Обмене»
  (`?open=exchange`), а администратора — на обмене с конкретным участником
  (`?open=exchange:anna`).

### 4.5. Путь файла через «Обмен» и уведомление

```
Администратор: «Отправить» файл для anna (браузер или мини-приложение)
   │
   ▼
rust-file-manager: файл → uploads/exchange/anna/from-admin/план.pdf
                   событие «файл для anna» → в память (последние 500 событий)
   │
   │  … до 10 минут …
   ▼
Бот: GET /internal/v1/events?after=<последний id>
     ← [{owner: anna, direction: from-admin, name: план.pdf, size,
         recipients: [Telegram anna]}]
   │
   ▼
Telegram anna: «📥 Администратор прислал вам файл план.pdf · 2 МБ» [📂 Открыть обмен]
   │
   ▼
anna открывает мини-приложение → «Обмен» → «Входящие» → Скачать / К себе / Удалить
```

В обратную сторону так же: файл от anna ложится в
`exchange/anna/from-user/`, а уведомление получает администратор.

Про доставку уведомлений:
- за один проход человек получает одно сообщение, даже если файлов несколько;
- после перезапуска бот начинает с текущего момента и старое не повторяет;
- события хранятся только в памяти файлового менеджера. Файл, пришедший после
  последней проверки и до перезапуска одной из программ, останется без
  уведомления, но сам файл никуда не денется;
- бот может написать только тому, кто хотя бы раз нажал у него «Старт».

## 5. Где реально лежат файлы

Всё хранится в одном каталоге `UPLOAD_DIR` на одной файловой системе.
Владелец всех файлов — пользователь службы `filemgr`.

```
/var/lib/rust-file-manager/
├── users.json                      # участники, хеши паролей, привязки Telegram, приглашения
└── uploads/                        # UPLOAD_DIR
    ├── shared/                     # 👥 «Общие файлы» — видят все вошедшие
    │   ├── Фото/                   #    категория выбирается по расширению
    │   ├── Документы/
    │   ├── Программы/
    │   ├── Видео/
    │   ├── Другие/
    │   │   └── Проект X/2026/…     #    подпапки, до 8 уровней
    │   └── Бэкапы/                 #    только вручную, при загрузке
    │       ├── Серверы/
    │       ├── HA/
    │       └── Project/
    ├── home/                       # 🔒 «Мои файлы» — у каждого свои
    │   ├── admin/                  #    администратор (имя = ADMIN_USERNAME)
    │   │   ├── Фото/ … Другие/
    │   │   └── Бэкапы/Серверы|HA|Project/
    │   ├── anna/
    │   └── bob/
    ├── exchange/                   # 🔁 «Обмен» — по папке на участника
    │   ├── anna/
    │   │   ├── from-admin/         #    администратор → anna
    │   │   └── from-user/          #    anna → администратор
    │   └── bob/
    │       ├── from-admin/
    │       └── from-user/
    └── .staging/                   # загрузки частями, которые ещё идут
        └── anna/<id>.part, <id>.json
```

### Кто что видит

| Каталог | Видят и скачивают | Загружают | Удаляют |
|---|---|---|---|
| `shared/…` | все вошедшие | все вошедшие | все вошедшие |
| `home/anna/…` | только anna | только anna | только anna |
| `exchange/anna/from-admin/` | anna и администратор | администратор | anna и администратор |
| `exchange/anna/from-user/` | anna и администратор | anna | anna и администратор |
| `.staging/anna/` | никто (служебный) | anna, частями | сама программа: после окончания загрузки или через сутки простоя |

- Участники не видят обмены друг друга: у anna нет доступа к `exchange/bob/`.
- Администратор через сайт и мини-приложение **не видит** чужие личные папки
  `home/<участник>/`. На самом сервере root видит всё — это надо понимать.
- Имя папки берётся из сеанса, а не из адреса запроса. Каждая часть пути
  проверяется: `..`, служебные имена и символические ссылки запрещены.

### Что происходит с файлом при действиях

| Действие | Что на диске |
|---|---|
| Загрузка в браузере | файл пишется сразу в выбранную категорию или папку. Если загрузка оборвалась, недописанный файл удаляется |
| Загрузка в мини-приложении | части копятся в `.staging/<логин>/<id>.part`. На последней части файл одним переименованием переезжает на место, поэтому недокачанный файл никогда не виден в списке |
| «Переместить» (браузер): «Общие» ↔ «Мои», между категориями и папками | переименование в пределах диска, без копирования. Файл с таким же именем не перезаписывается |
| Отправка в «Обмен» | файл ложится в `exchange/<участник>/from-admin/` или `from-user/` |
| «К себе» в «Обмене» | в `home/<я>/<категория по расширению>/` появляется жёсткая ссылка на тот же файл. Место на диске не удваивается, а удаление одной копии не трогает другую |
| Совпадение имён | существующий файл не перезаписывается: новый получает имя `план(1).pdf`, `план(2).pdf`… |
| Удаление | окончательное: корзины пока нет. Удалить можно только пустую папку |
| Удаление участника администратором | удаляются `home/<участник>/` и `exchange/<участник>/` |

Жёсткие ссылки и атомарные переименования работают только в пределах одной
файловой системы. Поэтому `uploads/` нельзя разносить по разным дискам или
точкам монтирования.

### Что не хранится на диске

- **Сеансы сайта и токены мини-приложения.** Они подписаны ключом из
  `SESSION_SECRET`. Отзыв («Завершить другие сеансы», отвязка Telegram,
  удаление участника) работает через счётчик в `users.json`.
- **События «Обмена».** В памяти файлового менеджера хранятся последние 500.
- **Позиция бота в событиях.** Хранится в памяти бота.

## 6. Секреты: где лежат и кто их знает

| Секрет | Где лежит | Кто знает | Для чего |
|---|---|---|---|
| `BOT_TOKEN` | `/opt/TelegramOnly/.env` | только бот | управление ботом в Telegram. Файловый менеджер его не знает |
| `ADMIN_PASSWORD_HASH` | `/etc/rust-file-manager/env` | файловый менеджер | вход администратора (bcrypt-хеш, не пароль) |
| `SESSION_SECRET` | `/etc/rust-file-manager/env` | файловый менеджер | подписи сеансов, токенов мини-приложения и ссылок `/d/` |
| `INTERNAL_API_TOKEN` = `FILES_SERVICE_TOKEN` | `/etc/rust-file-manager/env` и `/opt/TelegramOnly/.env` | обе программы | пропуск бота во внутренний API |
| Пароли участников | `users.json` | файловый менеджер | вход участников (bcrypt-хеши) |
| `TELEGRAM_BOT_ID` | `/etc/rust-file-manager/env` | все | не секрет: публичный номер бота, по нему проверяется подпись Telegram |

Файлы с секретами доступны только root (`600`). Их нельзя коммитить в Git,
пересылать в чат и выводить на экран целиком.

## 7. Что копировать в резервную копию

| Что | Путь | Без этого потеряется |
|---|---|---|
| Все файлы и участники | `/var/lib/rust-file-manager/` | общие, личные и обменные файлы, логины, привязки Telegram |
| Настройки файлового менеджера | `/etc/rust-file-manager/env` | пароль администратора, ключи сеансов (все выйдут), ключ для бота |
| Настройки бота | `/opt/TelegramOnly/.env`, `/opt/TelegramOnly/*_config.json` | токен бота, секреты API, конфигурации VPN-транспортов |

Для согласованной копии файлового менеджера остановите его на время
архивации: `tar` в [POST_DEPLOYwTELEGRAM.md](POST_DEPLOYwTELEGRAM.md) §1.2.
Жёсткие ссылки `tar` сохраняет, поэтому копия «К себе» не удваивает размер
архива. Храните копии вне сервера и в зашифрованном виде.
